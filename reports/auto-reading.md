# 日语歌词自动注音准确率比较

由于 `NextFire` 与 `MMS_FA` 等强制对齐模型只能接受拉丁字母（罗马字）输入，在对无注音的日语歌词进行自动打轴前，必须先将歌词中的日语汉字转换为准确的假名读音。

本实验在 **12 首日语主组歌曲**（合计 522 行正文，969 个含汉字的共同正文片段、490 行全假名参考行）以及混合歌曲 **`s11`《星》的前 10 行日语段落**上，对比了 **8 种本地自动注音方案**与 **2 种在线大语言模型（GPT-6.1 Terra）注音方案**的准确率。逐曲指标、逐片段预测与排除项明细保存在 [`results/reading/`](../results/reading/)。

## 核心发现

1. **在跨平台本地注音方案中，基于 `Sudachi` 的路线（Lazulite Studio 与 SUG Sudachi 模式）显著优于基于 `MeCab / UniDic`、`pykakasi` 或 `OpenJTalk` 的路线**：
   - Lazulite Studio（`Sudachi C 模式 + JmdictFurigana`）与 SUG（`Sudachi` 模式）按整行输入以充分利用句子上下文，在 12 首主组上的含汉字片段准确率分别达到 **94.22%** 和 **94.53%**，整行完全匹配率分别达到 **88.98%** 和 **89.59%**。
   - 相比之下，直接使用裸 `Sudachi`（不加词典拆分与规则优化）的整行匹配率为 82.65%；MiliKara 使用的 `UniDic` / `pykakasi` 路线整行匹配率仅为 **78.57% / 84.69%**；而 Timing 与 `OpenJTalk` 因为发音前端会将助词「は／を／う」转写为发音拼写「わ／お／ー」，且对复合词切分偏碎，整行书面匹配率分别只有 **46.94%** 和 **58.16%**。
2. **在 Windows 平台上，调用系统原生 `WinRT` 日语注音接口可进一步提高本地注音准确率**：
   - SUG 在 Windows 环境下默认调用系统 `WinRTAnalyzer`，其含汉字片段准确率达到 **96.49%**（935/969），整行完全匹配率达 **92.86%**（455/490），比跨平台 `Sudachi` 路线高出约 2 个百分点，但代价是绑定 Windows 系统组件且输出受操作系统版本影响。
3. **即便使用高推理强度的在线 LLM，仅凭文本也无法做到 100% 正确注音**：
   - `GPT-6.1 Terra`（`high` 推理强度）在直接注音和修正 Lazulite Studio 候选两种条件下，片段准确率均为 **97.63%**（946/969，仍有 23 个片段与原曲不一致），整行完全匹配率均为 **95.10%**（466/490），两种条件结果高度重合。
   - 剩余 ~2.4% 的差异主要来自日语歌曲中常见的**多音字／一词多读**（如「明日」读作 `あした`、`あす` 还是 `みょうにち`，「生命」读作 `いのち` 还是 `せいめい`）以及歌词特有的**训读／义读（当て字）**。在不听实际音频的情况下，任何纯文本模型都无法单靠字面确定歌手实际唱的是哪一种读音。

## 1. 12 首日语主组注音准确率对比

- **含汉字片段评估（分母：969 个片段）**：取全部 10 种方法与人工标注共有的正文词边界，筛除 481 个不含汉字的纯假名／符号片段和 13 个英文／非纯假名参考片段后，对 969 个含汉字片段比较完整假名读音。
- **整行评估（分母：490 行）**：在 522 行中取参考读音全部为假名的 490 行（排除 32 行含英文单词的行），要求整行所有汉字与助词的读音完全匹配。
- **CER（字符错误率，Character Error Rate）**：所有含汉字片段的 Levenshtein 编辑距离（插入、删除、替换字符数）之和除以参考假名总字数，越低越好。

| 注音方法 | 含汉字片段匹配 | 片段准确率 | 片段 CER | 整行完全匹配 | 整行完全匹配率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| **Lazulite Studio（Sudachi + JmdictFurigana）** | 913/969 | **94.22%** | 3.03% | 436/490 | **88.98%** |
| Sudachi（直接取 C 模式 `reading_form`） | 882/969 | 91.02% | 6.47% | 405/490 | 82.65% |
| MiliKara（UniDic） | 896/969 | 92.47% | 3.37% | 385/490 | 78.57% |
| MiliKara（pykakasi 回退） | 891/969 | 91.95% | 3.97% | 415/490 | 84.69% |
| Timing（原生 UniDic + 发音覆盖规则） | 761/969 | 78.53% | 6.88% | 230/490 | 46.94% |
| OpenJTalk（`pyopenjtalk` 1.11 词典） | 781/969 | 80.60% | 6.23% | 285/490 | 58.16% |
| **SUG（跨平台 Sudachi 模式）** | 916/969 | **94.53%** | 2.74% | 439/490 | **89.59%** |
| **SUG（Windows 原生 WinRT）** | 935/969 | **96.49%** | 2.13% | 455/490 | **92.86%** |
| **GPT-6.1 Terra 直接注音** | 946/969 | **97.63%** | **1.36%** | 466/490 | **95.10%** |

## 3. 各方法调用说明与评分归一化口径

### 3.1 各注音方案实现方式

| 方法 | 实现与调用说明 |
| --- | --- |
| **Lazulite Studio** | 使用 `SudachiPy` C 模式整行分词选读，再结合 `JmdictFurigana` 词典将整词读音精确拆分到每个汉字片段。 |
| **Sudachi** | 直接调用 `SudachiPy` C 模式分词并拼接每个词的 `reading_form()`，不使用 `JmdictFurigana` 后处理。 |
| **MiliKara（UniDic / pykakasi）** | 分别测试 MiliKara 原生 `rule_segments`（显式加载完整 `UniDic` 词典）与其回退路径 `pykakasi`。 |
| **Timing** | 调用 Timing 原生 `tokenize(text, fine=False)`（基于 `UniDic`）及其数字、外来语和歌唱发音覆盖规则。 |
| **OpenJTalk** | 调用 `pyopenjtalk.run_frontend`（固定 `open_jtalk_dic_utf_8-1.11` 词典）提取发音序列。 |
| **SUG（Sudachi / WinRT）** | 调用 SUG 原生 `PronunciationResolver.resolve_project(fill_missing=True)`：在 Linux 下使用其跨平台 `SudachiAnalyzer`；在独立 Windows 环境下使用系统 `WinRTAnalyzer`（`--require-winrt`）。 |
| **GPT-6.1 Terra（直接 / 修正）** | 使用 `gpt-6.1-terra`（`high` 推理强度），在仅提供歌词正文文本（不提供音频、参考答案或外部网络）的条件下，先生成直接注音，再基于 Lazulite Studio 的自动注音候选进行审查修正。 |

### 3.2 归一化与评分口径

- 输入从原始 TTML 提取纯文本正文（清除 XML 缩进换行，保留行内正常空格），所有人工 Ruby 注音在输入前剥离。
- 比较读音时，统一执行 NFKC 归一化、片假名转平假名，并移除标点与空白字符；保留促音／拗音小假名、长音符（`ー`）与原始助词拼写（「は／を／う」）。
- 注意：本报告评估的是**书面 Ruby 注音的一致性**。Timing 与 OpenJTalk 将助词「は／を」转换为发音「わ／お」、或将长音「う」转为「ー」，在面向声学对齐的罗马化阶段中部分差异会被抵消，但作为呈现给用户的歌词 Ruby 注音则属于拼写不一致。
